# Hareru Godot 전환 로드맵 · 작업 규칙

> 상태: 확정 (2026-11-03). 결정 D1~D5는 기본값대로 소유자 확정.
> 이 문서는 Godot 전환 작업의 **가이드라인**이다. 새 작업 세션은 이 문서를 먼저 읽고 시작한다.
> 기획 내용 자체는 [GAME_DESIGN.md](../Archive/GAME_DESIGN.md) · [STORY_BIBLE.md](../Archive/STORY_BIBLE.md)가 원본이고, 이 문서는 **순서와 규칙**만 다룬다.

## 0. 왜 이 순서인가

게임 개발의 표준 순서는 **설계 → 프로토타입(스파이크) → 버티컬 슬라이스 → 제작 → 다듬기**다.

- 처음 제안했던 "기반 코드부터"는 엔지니어 관점의 순서였다. 게임은 **재미와 느낌을 먼저 확인**하고, 그 확인에 **필요한 만큼만** 기반을 만든다.
- 기반을 먼저 크게 만들면, 슬라이스에서 설계가 바뀔 때 기반도 같이 버려진다.
- 그래서 기반 코드(상태 머신, 저장, 테스트)는 따로 하는 단계가 아니라 **버티컬 슬라이스 안에 들어간다.**

```
P0 스파이크 ✅ → P1 설계 고정 → P2 버티컬 슬라이스 → P3 제작 → P4 다듬기 · 출시
```

### P2. 버티컬 슬라이스 — Day 1을 최종 품질로
목표: Day 1을 처음부터 끝까지, **설명 없이** 한 사람이 플레이할 수 있다.

| 영역 | 할 일 | 관련 개념 |
| :--- | :--- | :--- |
| 게임 흐름 | 화면 상태를 enum 상태 머신 하나로 (연구소 / 대화 / 판독 / 퇴근) | State Machine |
| 연결 | 신호(signal) · 이벤트 버스로 장면끼리 연결, 직접 참조 최소화 | Event-Driven Architecture |
| 저장 | FSRS 기록 + 오늘 대기열 + 스토리 진행 저장. 저장 파일에 **버전 번호**와 이전(migration) 함수 | Persistent / Transient State, Save/Load Serialization |
| 데이터 | 단어 · 스토리를 Tools 파이프라인에서 Godot용으로 바로 내보냄 | Data-Driven Design, Single Source of Truth |
| 테스트 | FSRS · 세션 · 저장을 창 없이 자동 검사 (GUT 애드온 또는 자체 러너) | Headless Testing, Regression Testing |
| 그림 · 소리 | 기준표대로 만든 Day 1 에셋으로 교체, Day 1 음성 연결 | Environmental Storytelling |
| 느낌 | 손잡이 · 키 · 도장 · 종이 이동의 반응 다듬기 (짧고 빠르게) | Game Feel, Juice |
| 그리기 순서 | 인물이 움직이는 장면은 Y 정렬 | Depth Sorting |
| 기본 접근성 | 키보드만으로 전부 조작, 글자 크기 옵션, 움직임 줄이기 옵션 | Accessibility |

완료 기준:
1. Day 1을 시작부터 끝까지 막힘 없이 플레이할 수 있다.
2. 중간에 꺼도 다시 켜면 이어진다.
3. 테스트가 창 없이 전부 통과한다.
4. 소유자가 "SwiftUI 앱보다 낫다"고 판단한다 → 이때 Swift 앱을 보관(archive) 처리.

## 3. 작업 규칙 (Claude가 지키는 가이드라인)

1. **한 단계, 한 목표.** 단계 밖의 일은 하지 않고 [BACKLOG.md](BACKLOG.md)에 적는다.
2. **화면을 바꾸는 작업은 시안 확정이 먼저.** 시안 없이 겉모습만 고치는 반복을 하지 않는다.
3. **스파이크 코드는 옮겨 쓰지 않는다.** `Game/`의 코드는 테스트와 함께 새로 쓴다. (알고리즘은 참고 가능)
4. **원본은 한 곳.** 단어 · 스토리는 `Tools/` 파이프라인이 원본, FSRS는 D2 이후 `Game/`에만.
5. **매 작업은 실행 가능한 상태로 끝낸다.** 창 없는 테스트 통과 + 스크린샷 인자(`--shot`)로 화면 확인 후 보고.
6. **단계마다 새 세션.** 긴 세션은 맥락이 요약되며 세부를 놓친다. 새 세션은 이 문서 + 해당 단계 표를 설명서로 받는다.
7. **커밋은 Claude가 작업 단위마다 알아서** (2026-11-04 소유자), 파일을 지정해서 스테이징한다 (`git add -A` 금지). push · 브랜치 전환 · 삭제 같은 우려되는 일만 먼저 묻는다. API 키는 저장소에 넣지 않는다.
8. **보고는 한국어로,** 무엇이 됐고 무엇이 안 됐는지 그대로.
9. **공부 기록.** 단계마다 새로 배운 개념은 [Study/](../../Study/README.md)에 글로 남긴다.

### 3-1. 에셋 제작 규칙 (2026-11-03 소유자 확정)

1. **기준:** [ART_STYLE_SHEET](../05_Art/ART_STYLE_SHEET.md) + 확정된 인물(주임 C5, 주인공 H1). 소유자가 준 참고 이미지가 있으면 그게 최우선.
2. **세트 단위:** 에셋은 세트로 묶는다 (예: ① 인물 행동 ② Day 1 물건 ③ 연구소 배경 · 조명).
3. **대표 샘플 먼저:** 세트마다 대표 1장을 만들어 소유자 승인을 받는다. **승인 전에는 세트 나머지를 만들지 않는다.**
4. **승인 후:** 대표 샘플을 스타일 기준 이미지로 써서 나머지를 Claude가 만들고 고른다. 지저분한 픽셀은 `pixelart_workbench`로 정리.
5. **횟수 상한:** 세트당 Pixellab 생성 30회. 넘길 것 같으면 멈추고 알린다.
6. **도구 분담:** 인물 · 복잡한 그림 = Pixellab. 키 · 스탠드 · 종이 · 작은 UI 같은 단순한 물건 = `pixelart_workbench`로 직접 그림 (크레딧 0).
7. **보고:** 완성된 세트를 비교표 한 장으로 보여 주고, 소유자가 짚은 것만 다시 만든다.
8. **빛 · 효과는 그림으로 만들지 않는다:** 조명 전후, 비, 먼지, 레이저는 Godot 조명 · 파티클 · 셰이더로 처리해 그림 수를 줄인다.
