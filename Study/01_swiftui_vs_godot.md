# 01. SwiftUI에서 막히고 Godot에서 풀린 이유

> 질문: 판독 화면을 다이제틱 UI로 만드는 게 SwiftUI(+SpriteKit)에서는 몇 번을 해도 "그냥 화면"이었는데,
> Godot에서는 한 시간 만에 됐다. SwiftUI가 병목이었나? 게임 전용 엔진 하나라서 잘 된 건가?
>
> 짧은 답: **반은 맞고 반은 아니다.** 도구가 문제의 모양과 안 맞았던 것(진짜 원인)과,
> 비교 자체가 공정하지 않았던 것(착시)이 섞여 있다. 둘을 나눠서 봐야 다음에도 같은 판단을 할 수 있다.

---

## 1. 진짜 원인: 도구의 "기본 단위"가 문제와 달랐다

### SwiftUI의 기본 단위 = 화면 위의 상자 (선언형 레이아웃)

SwiftUI는 "상태가 이러면 화면은 이렇게 생겼다"를 선언하는 도구다.

```swift
VStack {
    Text(word.term)
    if revealed { Text(sense.meaning) }
    Button("정답 보기") { revealed = true }
}
```

- 모든 것이 **부모가 자식에게 크기를 제안하고 자식이 답하는 레이아웃 트리** 안에 있다.
- "카메라", "월드 좌표", "책상 위 어디쯤"이라는 개념이 없다. 있는 건 화면 안의 사각형뿐이다.
- 그래서 카메라가 책상으로 다가가는 연출을 하려면 `scaleEffect` + `offset` + `GeometryReader`로 **흉내**를 내야 한다.
  흉내는 금방 깨진다 (안전 영역, 화면 크기, 스크롤 뷰와 섞이면 특히).

이 앱이 원래 "단어 카드 앱"이었을 때는 이게 완벽하게 맞는 도구였다. 카드 = 화면 위의 상자니까.

### Godot의 기본 단위 = 세계 안의 물체 (씬 그래프 + 카메라)

```gdscript
var t := create_tween().set_parallel()
t.tween_property(camera, "position", desk_position, 0.9)
t.tween_property(camera, "zoom", Vector2(2.2, 2.2), 0.9)
```

- 연구소 그림, 책상, 판독기, 종이가 모두 **좌표를 가진 물체(노드)** 이고, 화면은 그 세계를 비추는 **카메라** 결과다.
- "책상으로 다가간다" = 카메라 위치와 배율을 바꾼다. 흉내가 아니라 그 자체다.
- 레이어(`CanvasLayer`), 트윈(`Tween`), 셰이더, 입력, 매 프레임 그리기(`_draw`)가 **한 모델 안에** 있다.

다이제틱 UI = "UI가 세계 안의 물건이다"라는 뜻이다. 문제의 기본 단위가 "세계 안의 물체"이니,
그걸 기본 단위로 가진 도구가 유리한 건 당연하다. **이건 착시가 아니라 진짜 원인이다.**

### SwiftUI + SpriteKit 조합이 특히 힘들었던 이유

"그럼 SpriteKit(애플의 2D 게임 엔진)을 쓰면 되잖아?" — 실제로 연구소 화면은 SpriteKit으로 만들었다.
문제는 **두 세계를 이어 붙이는 비용**이었다.

| 문제 | SwiftUI | SpriteKit |
| :--- | :--- | :--- |
| 좌표계 | 왼쪽 위가 원점, y는 아래로 | 왼쪽 아래가 원점, y는 위로 |
| 상태 | `@Observable`, 바인딩 | `SKScene` 안의 노드 속성 |
| 글자 | 강함 (후리가나, 줄바꿈, 접근성) | 약함 (`SKLabelNode`는 루비·서식이 거의 안 됨) |
| 애니메이션 | `withAnimation`, 레이아웃 기반 | `SKAction`, 프레임 기반 |

일본어 단어 앱은 글자가 핵심이라, 글자는 SwiftUI에 두고 배경·캐릭터는 SpriteKit에 뒀다.
그러면 **"종이는 SwiftUI, 책상은 SpriteKit"** 이 되고, 둘을 같은 장면처럼 움직이게 하려면
좌표 변환 + 상태 동기화 + 애니메이션 타이밍을 매번 손으로 맞춰야 한다.
결국 종이(카드)는 늘 화면 위에 **떠 있는** SwiftUI 패널이 됐다. 이게 "그냥 화면" 느낌의 정체다.

Godot에서는 후리가나를 직접 만들었다 ([ruby_text.gd](../GodotSpike/scripts/ruby_text.gd), 약 120줄).
글자도 세계 안의 물체라서, 종이와 같이 기울고, 같이 날아가고, 같은 셰이더를 받는다.

## 2. 착시: 비교가 공정하지 않았던 부분

같은 결과를 "Godot이 좋아서"라고만 기억하면 다음에 틀린 판단을 한다.

### (1) 백지에서 시작했다 — 경로 의존성(path dependency)

SwiftUI 쪽은 이미 탭 바, 카드 뷰, 대시보드, Liquid Glass 테마가 있는 코드베이스였다.
"프론트를 갈아엎자"고 해도 실제 작업은 **있는 구조를 고치는 방식**으로 흘러갔다
(빗방울 오버레이를 지우는 대신 색만 바꾸고, 탭 바를 없애는 대신 모양만 바꾸는 식).
기존 코드가 다음 결정을 끌어당기는 현상을 경로 의존성이라고 한다.
Godot 쪽은 빈 폴더였으니 이 힘이 0이었다. **같은 SwiftUI라도 빈 프로젝트에서 시작했으면 결과가 꽤 달랐을 것이다.**

### (2) 컨셉은 이미 정해져 있었다

"연구소 단면 → 책상 → 판독기 → 레이저 → 실물 키"라는 그림은 SwiftUI 시기의 시행착오와 대화에서 나왔다.
Godot 쪽은 **정해진 답을 구현만** 했다. 디자인을 찾는 시간과 구현하는 시간은 다르다.

### (3) 범위가 훨씬 작았다

스파이크(spike)는 질문 하나에 답하려고 만드는 버리는 코드다. 이번 질문은 "다이제틱 판독 장면이 되나?"였다.
그래서 Godot 쪽에는 다음이 **없다**: 온보딩, 설정, 기록 화면, 저장 데이터 이전, 단위 테스트,
VoiceOver(접근성), 알림, iOS 앱 생명주기, 앱스토어 심사 대응. SwiftUI 앱에는 이게 다 있다.

### (4) 확인 루프가 짧았다

- SwiftUI: 빌드 수십 초 → 시뮬레이터 실행 → 탭으로 화면까지 이동 → 스크린샷.
- Godot: `godot --path . -- --shot=a.png --desk --reveal` 한 줄로 실행 → 원하는 상태 → 스크린샷 → 종료 ([main.gd](../GodotSpike/scripts/main.gd)의 `_run_shot_args`).

눈으로 확인하는 루프가 짧을수록 시도를 많이 할 수 있다. 이건 엔진 덕도 있지만, **확인 장치를 처음부터 만들어 둔 덕**이 더 크다.
SwiftUI에서도 프리뷰나 스냅샷 테스트로 비슷하게 만들 수 있다.

### (5) "게임 전용 언어"라서가 아니다

GDScript가 Swift보다 뛰어난 언어는 아니다. 타입 시스템은 오히려 약하다
(이번에도 `enum Button`이 엔진의 `Button` 클래스와 이름이 겹쳐서 에러가 났다).
차이는 언어가 아니라 **엔진이 기본으로 주는 개념**(씬 트리, 카메라, 트윈, 셰이더)이다.

## 3. 정리: 언제 무엇을 고르나

| 만들려는 것 | 기본 단위 | 맞는 도구 |
| :--- | :--- | :--- |
| 목록, 폼, 설정, 카드 넘기기 | 화면 위의 상자 | SwiftUI, UIKit, Flutter |
| 카메라가 움직이는 세계, 물건이 곧 UI | 세계 안의 물체 | Godot, Unity, SpriteKit(단독) |
| 둘 다 반반 | — | 어느 쪽이 **주인**인지 먼저 정하기 |

Hareru는 처음엔 1행이었고, "기억하는 단어로만 말하는 세계"와 다이제틱 UI로 가면서 2행으로 옮겨 갔다.
문제가 바뀌었는데 도구는 그대로였던 것이 핵심이다.

일반화하면:
1. **문제의 기본 단위를 먼저 말로 적어 본다.** ("화면 위의 상자"인가, "세계 안의 물체"인가)
2. 그 단위를 기본으로 가진 도구를 고른다. 흉내 내야 하는 도구는 피한다.
3. 큰 결정 전에는 **스파이크**로 확인한다. 질문 하나, 버릴 코드, 짧은 시간.
4. 결과를 비교할 때는 범위·출발점·확인 루프가 같았는지 따진다.

## 4. Godot으로 옮길 때 잃는 것 (공정하게)

- **iOS 네이티브 기능**: 위젯, 알림, 단축어, VoiceOver 같은 접근성. Godot은 기본 지원이 약하다.
- **글자 처리**: 후리가나·일본어 입력(IME) 등을 직접 만들거나 다듬어야 한다.
- **테스트 습관**: Swift의 XCTest처럼 바로 쓰는 틀이 약하다 (GUT 같은 애드온은 있다).
- **이미 만든 코드**: FSRS는 옮겼지만(약 100줄), 세션 엔진·스토리 엔진·저장은 다시 써야 한다.

반대로 얻는 것: 씬 편집기, 카메라·트윈·셰이더·파티클, 데스크톱/모바일 동시 출력, Pixellab 그림을 그대로 쓰는 흐름.

## 6. 직접 해 볼 것

1. [fsrs.gd](../GodotSpike/scripts/fsrs.gd)와 `FSRSEngine.swift`를 나란히 놓고 한 함수씩 대응시켜 읽기. 같은 알고리즘이 두 언어에서 어떻게 생겼는지.
2. [scan_reveal.gdshader](../GodotSpike/shaders/scan_reveal.gdshader)의 `3.0`(덩어리 크기)과 `0.08`(안 드러난 부분의 투명도)을 바꿔 보고 느낌 비교하기.
3. SwiftUI로 "카메라가 다가가는" 효과를 30줄 안에서 흉내 내 보고, 어디서 깨지는지 직접 확인하기 (화면 회전, 스크롤 뷰 안에 넣기).
4. 같은 판독 장면을 SpriteKit 단독(SwiftUI 없이)으로 만든다면 후리가나를 어떻게 할지 설계만 해 보기.
